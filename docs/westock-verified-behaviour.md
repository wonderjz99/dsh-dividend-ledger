# westock 真实行为核对记录

> 核对日期：**2026-10-10**  
> CLI 版本：`westock 0.0.2 channel=skillhub`（`/Users/jim/.local/bin/westock`）  
> 方法：装真 CLI、跑真请求、把原始输出落盘到 [`../../data/raw/`](../data/raw/)  
> 结论：**Skill 文档与实际输出有 6 处不符，且发现 2 个文档完全没提的行为**。

---

## 1. 最重要的发现：没有 JSON 输出

```
$ westock dividend sh600519 --format json
Error: unknown flag: --format
```

全局与子命令都**没有** `--format` / `--json` 之类的结构化输出开关。
唯一可用的形态是 **Markdown 表格**。

**影响**：阶段一写的 `parse_dividend_payload()` 是按 JSON 设计的，**不能用了**，
必须改成 Markdown 表格解析器。阶段二的真实工作量比计划里估的大。

## 2. 限频会静默失败（退出码仍为 0）

```
$ westock dividend sh600519 --years 1 > out.txt
$ wc -l out.txt
1
$ cat out.txt
请求过于频繁，请稍后再试
$ echo $?
0
```

**这是最危险的行为**：请求过频时 CLI 把一句中文提示写进 stdout，
**退出码是 0**，stdout 只有一行、不是表格。

**后果**：如果解析器不识别这句话，会把它当成"这只股票没有分红数据"，
于是**账本静默少算分红**。

**要求**：解析器必须显式识别该提示并抛 `ProviderError`，绝不能返回空列表。
（已写进实现与测试。）

限频实测：连续 16 次请求即触发。冷却约 45 秒后恢复。
**结论**：批量取数必须加间隔（实测 8 秒间隔可稳定跑 3 只）。

## 3. 字段名：文档与实际的差异（A 股）

| 文档写法 | **实际输出** | 影响 |
|---|---|---|
| `procedure` = "实施" | **"方案实施"** | 我原先的排除关键词里有"预案"、"取消"等，不含"方案实施"→ 不误杀，但**判断"是否实施"的逻辑要按实际值写** |
| `procedure` 取值含"预案" | **普查 47 行全部是"方案实施"，一行预案都没有** | 见下方 §3.1：本数据源**取不到**预案，阶段三的 `proposed` 分支在此源上无法实测 |
| `dividendFlag` = `0`/`1` | **"是"** | 按 `0/1` 解析会全错 |
| `bonusShareRatio` 无值 | **空字符串**（不是 `0`、不是 `null`） | 解析空串为 0 是必须的 |
| `tranAddShareRatio` 无值 | **空字符串** | 同上 |
| `dividendType` | 有分红 / **特殊分红** | 特殊分红也是现金分红，不能漏 |
| 字段列表含 `reportEndDate` | 实际存在，且**同一 reportEndDate 可对应期中与年度多次派息** | 不能拿它当唯一键 |

### 3.1 普查结论：本数据源不返回预案

**核对方法**：对 8 只 A 股（`sh600519` `sz000001` `sz300750` `sh601318` `sh600036`
`sh601398` `sh600030` `sz002594`，覆盖白酒/银行/电池/保险/券商）分别跑
`--years 1 --all` 与 `--years 6`，共 11 个真实载荷、**47 个数据行**。

| 观察项 | 结果 |
|---|---|
| `procedure` 取值集合 | **仅 `{方案实施}`** |
| 含"预案/取消/终止"的行 | **0 行** |
| `proposalSn` 取值集合 | `{1, 2}`（2 = 特殊分红） |
| 除权日**晚于**核对日（2026-10-10）的行 | **0 行** |

**两条结论**：

1. **`--all` 在本数据源上没有带来任何预案行。** 文档说它"包含未实施分红方案"，
   但 A 股实测取不到——`--all` 与不带 `--all` 的差别在本样本里是 0 行。
   → 阶段三的 `proposed`（董事会预案）分支**在这个数据源上无法落地**，
   要么换源（Tushare `div_proc`），要么靠手工录入。
2. **本次抽样没有"未来除权日"的行**，所以 `confirmed`（已公告未实施）
   在真实数据上也没被覆盖到。这是**抽样时点的现实**（最新一条是
   平安银行 2026-09-24，已实施），不是实现缺陷——
   状态逻辑由离线单测覆盖，代码路径是通的。

**对阶段三的影响**：`status` 在本数据源上实际只会出现 `implemented`。
"未来预期分红"的能力**仍然成立但要换数据源**——这一点必须让用户知道，
不能假装 westock 能给。

## 4. 同一天可能有多条分红记录（会丢数据）

宁德时代同一除权除息日出现两行：

```
|  | 21.78 | 是 | 10派21.780元 | 有分红   | 20260422 | 方案实施 | 1 | 20251231 | 20260421 |  9870909056.32 |  |
|  | 47.79 | 是 | 10派47.790元 | 特殊分红 | 20260422 | 方案实施 | 2 | 20251231 | 20260421 | 21658895491.34 |  |
```

同一天：`proposalSn=1` 的普通分红 + `proposalSn=2` 的特殊分红。

**影响**：阶段一的自然键是 `(code, ex_date)`，会把这两条**合并成一条**，
丢掉 30.01 元/10 股的分红。**必须把 `proposalSn` 纳入唯一键。**

茅台 2024-04-30 与此同理（20.11 + 30.17）。

## 5. `方案实施` 的行会有**未来**的除权日

| 股票 | 除权除息日 | 状态 |
|---|---|---|
| sz000001 平安银行 | 2026-09-24 | 早于今天（2026-10-10）→ 已实施 |
| sz300750 宁德时代 | 2026-08-10 | 已实施 |
| sh600519 茅台 | 2026-06-26 | 已实施 |

核对当天为 **2026-10-10**，三只股票都**没有**未来除权日的记录。
但公开数据确实会提前公布实施日——`方案实施` + 未来 `exDiviDate` 就是
"已公告未实施"的形态，这正是阶段三"待收分红"的数据来源。

**因此状态不能只看 `procedure` 文本，必须结合日期**：

| 情形 | 状态 |
|---|---|
| `procedure` 含"预案/取消/终止/否决/不分配" | `proposed`（或不采用） |
| `procedure` = 方案实施 且 `exDiviDate <= 今天` | `implemented` |
| `procedure` = 方案实施 且 `exDiviDate > 今天` | **`confirmed`**（已公告未实施） |

## 6. 量纲再次确认（第三重独立验证）

用 `totalCashDiviComRMB ÷ (cashDiviRMB ÷ 10)` 反推总股本：

| 股票 | 反推股本 | 真实总股本 | 结论 |
|---|---|---|---|
| sh600519 茅台 | 1,256,197,800 | ≈12.56 亿 | ✅ 吻合 |
| sz300750 宁德时代 | 2,442,311,158 | ≈24.4 亿 | ✅ 吻合 |

若 `cashDiviRMB` 是每股口径，反推股本会只有 1/10（1.26 亿 / 2.44 亿），
与真实股本差一个数量级。**`cashDiviRMB` 是"每 10 股"确认无疑。**

`tranAddShareRatio = 8.00` 对应方案原文"10派25.200元**转8.000股**"，
确认送转比例也是**每 10 股**口径。

## 7. 多代码批量与日期范围

- `westock dividend sh600519,hk00700,usAAPL` 支持逗号分隔多代码（见 `--help` 示例）。
- `--years N` 默认 **1 年**；`--all` 包含未实施方案。
- 输出按除权除息日**升序**排列（实测）。
- 数值格式：金额保留 2 位小数（`239.57`）；送转比例保留 2 位（`8.00`）；
  方案原文里现金保留 3 位（`10派239.570元`）。
